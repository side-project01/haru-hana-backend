# Daily Card Tasks Runner

데일리 카드 백엔드에서 `TASKS.md`의 미완료 작업을 **Phase 단위**로 구현하고, 매 Phase마다
**명세 검토(CLAUDE.md + PRD) → 빌드/테스트 검증 → `[x]` 처리**를 수행한다. 진행 중 발생한
모호함·보안 우려·오류·예측 불가 상황은 레포 루트 `ISSUES.md`에 기록한다.

이 스킬은 이 레포에 특화돼 있다. 일반 프로젝트용 글로벌 `tasks-runner`와 달리, 이 프로젝트의
빌드 명령(`npm run build` = `nest build`), TASKS.md 포맷(`## Phase N` 아래 `- [ ]` 불릿, TASK-ID 없음),
그리고 두 SSOT 문서(`.claude/CLAUDE.md`, `docs/PRD_Daily_Card.md`)를 기준으로 동작한다.

## 전체 흐름

```
[1] TASKS.md 파싱 → ## Phase 단위 미완료 `- [ ]` 수집, 진행 상태 요약
[2] 실행 순서 결정 → Phase 오름차순, Phase 내 위→아래
[3] 한 Phase의 작업들을 구현      ← 이 시점엔 [x] 안 함
[4] 명세 검토 → CLAUDE.md 컨벤션 + PRD(P1~P7) 준수 확인
       └ 수정 가능 → 수정 후 재검토 / 모호·보안·미해결 → ISSUES.md 기록
[5] 빌드 & 테스트 → npm run build → npm test → 오류 수정 → 재실행
[6] [4]·[5] 모두 통과 → 해당 Phase의 [ ] → [x]
[7] 다음 Phase 반복 → 마지막에 완료 보고
```

**핵심 원칙**: 구현만으로는 절대 `[x]` 처리하지 않는다. **명세 검토 + 빌드 + 테스트**까지 모두
통과해야 그 Phase를 `[x]`로 표시한다. 단위는 항상 **Phase**다 — 작업 하나하나가 아니라 Phase가
끝났을 때 검토/검증/체크를 한 번에 한다.

---

## Step 1: TASKS.md 파싱

`TASKS.md`를 읽어 다음을 추출한다.

- **Phase 헤더**: `## Phase N — ...` (그리고 끝의 `Validation`/`주의·리스크` 같은 섹션)
- **미완료 작업**: `- [ ]` 로 시작하는 불릿 (이 레포는 `TASK-XXX` 같은 ID가 없다)
- **완료 작업**: `- [x]` 불릿 → 건너뛴다
- **권장 순서**: TASKS.md에 별도 "구현 순서" 안내가 있으면 따른다

시작 전 상태를 요약 출력한다:
```
총 작업 24개 중 완료 0개, 미완료 24개
Phase 0부터 시작 (4개 작업)
```

## Step 2: 실행 순서 결정

Phase 번호 오름차순으로 진행하고, 한 Phase 안에서는 TASKS.md에 적힌 위→아래 순서대로 구현한다.
앞 Phase가 완전히 통과(`[x]`)되기 전에는 다음 Phase로 넘어가지 않는다.

## Step 3: 작업 구현 (Phase 단위)

현재 Phase의 작업을 하나씩 구현한다. 진행 상황을 짧게 출력한다:
```
[Phase 0] 의존성 설치 중...
[Phase 0] config/env.validation.ts 작성 완료 (검토 대기)
```

### 구현 원칙 (CLAUDE.md 1장과 일치)
- **작업 설명에 명시된 것만** 구현한다. 지금 필요 없는 추상화·미래 확장 코드는 만들지 않는다.
- 여러 작업이 같은 파일을 건드리면 이미 만든 파일에 누적해서 추가한다.
- 비밀값이 필요하면 코드에 넣지 말고 `.env.example` 패턴을 따른다(시크릿은 환경변수).
- feature 기반 폴더 구조(`src/modules/<feature>/`)와 네이밍 규칙을 지킨다.

**이 시점에 `[x]` 처리하지 않는다.** Phase의 모든 작업 구현이 끝나면 Step 4로 간다.

## Step 4: 명세 검토 (이 스킬의 핵심)

Phase 구현이 끝나면, **실제 구현을 두 SSOT 문서와 대조**한다. 검토 시점에 두 문서를 직접 읽어
최신 내용을 기준으로 삼는다(기준을 기억에 의존하거나 하드코딩하지 않는다).

- `.claude/CLAUDE.md` — 개발 컨벤션
- `docs/PRD_Daily_Card.md` — 기획 명세(정책 P1~P7)

> CLAUDE.md는 PRD를 `docs/PRD_데일리카드.md`로 링크하지만 실제 파일명은 `docs/PRD_Daily_Card.md`다.
> 실제 파일을 읽고, 이 파일명 불일치는 첫 실행 시 ISSUES.md에 "문서 불일치"로 한 번 기록한다.

### CLAUDE.md 컨벤션 체크리스트 (우선순위 높은 항목)
무엇을 먼저 볼지에 대한 가이드일 뿐, 검토는 문서 전체 기준이다.

- **구조/네이밍(2·3장)**: feature 기반 폴더, 파일·클래스·DTO 네이밍 규칙, 도메인 폴더 복수형
- **레이어 책임(4장)**: 컨트롤러는 얇게(라우팅·DTO 매핑만), 서비스는 `req`/`res` 등 HTTP 객체에
  의존하지 않음, Prisma는 데이터 접근만(비즈니스 판단 금지)
- **DTO·검증(5장)**: 요청/응답 DTO 분리(엔티티 그대로 노출 금지), class-validator 적용,
  전역 ValidationPipe(whitelist·forbidNonWhitelisted·transform)
- **설정·보안(6장)**: Zod 환경변수 검증 + fail-fast, Helmet(다른 미들웨어보다 먼저)·CORS
  화이트리스트, 쿠키 기반 익명 ID(httpOnly·secure, 시크릿은 env), 금칙어 필터(P6)
- **로깅(7장)**: 답변 본문·익명ID 원문·시크릿·환경변수 값을 로그에 남기지 않음
- **Prisma·날짜(8장)**: 스키마는 마이그레이션으로만, `PrismaService` 주입,
  P1 `@@unique([anonId, serviceDate])`, P5 본인 제외 무작위 1건, **P7 KST 자정 serviceDate를
  `common/`의 단일 유틸로** 계산(날짜 로직 분산 금지)

### PRD 체크리스트
이번 Phase가 건드리는 정책(P1~P7)이 의도대로 구현됐는지 확인한다. 예: 하루 1회 제출(P1),
무로그인 익명 식별(P2), 1일 1질문(P3), 클릭 저장(P4), 타인 답변 무작위 1건(P5), 금칙어 차단(P6),
KST 자정 기준 날짜(P7).

### 검토 결과 출력 형식
```
## [Phase N] 명세 검토 결과

### 수정 필요
- <파일>:<줄> — <문제> (위반: CLAUDE.md X장 / PRD Pn)
  수정: <해결 방법>

### 주의 권고
- <파일>:<줄> — <권고 내용>

### 양호
- <잘 구현된 부분>
```

- **수정 필요** 항목은 즉시 수정한 뒤 다시 검토한다.
- 수정하기 모호하거나, 보안 위험이 있거나, 자체적으로 해결하지 못하는 항목은 **ISSUES.md에 기록**한다
  (아래 "ISSUES.md 기록 규칙" 참조).

## Step 5: 빌드 & 테스트 검증

명세 검토를 통과(또는 미해결 항목을 ISSUES.md에 기록)했으면 다음을 순서대로 실행한다.

```bash
npm run build   # nest build — 컴파일·문법 오류 확인
npm test         # jest — 단위 테스트
```

- 오류가 나면 메시지를 읽어 원인을 파악하고 수정한 뒤 재실행한다. 무오류가 될 때까지 반복한다.
- `npm run lint`는 `--fix`가 걸려 있어 검사 겸 자동수정이 일어난다. 컨벤션 정렬이 필요하면 선택적으로
  실행한다(필수 아님).
- **테스트가 아직 없는 Phase**(스펙 파일 부재)는 `npm test`를 "테스트 없음"으로 간주하고 통과 처리한다.
  없는 테스트를 강제로 만들지 않는다(작업 범위 밖).

### 인프라 미비로 인한 실패는 무한 수정하지 않는다
Prisma 미초기화, 의존성 미설치 등으로 초기 Phase(특히 Phase 0)에서 build/test가 실패하는 것은
정상일 수 있다. 실패 원인이 **"아직 구성되지 않은 인프라"**라고 판단되면 자체 해결을 반복하지 말고,
ISSUES.md에 "예측 불가 / 인프라 미비"로 기록한 뒤 보고하고 진행한다. **코드 오류와 인프라 미비를
구분**하는 것이 중요하다 — 코드 오류면 고치고, 인프라 미비면 기록한다.

### 검증 결과 출력 형식
```
[Phase 0 빌드] nest build: ✓ 오류 없음
[Phase 0 테스트] jest: 테스트 없음 (통과 간주)
[Phase 1 빌드] nest build: ✗ src/...:12 - TS2345 ...
  → 수정 중...
  → 재실행: ✓ 오류 없음
```

## Step 6: TASKS.md `[x]` 처리

Step 4(명세 검토)와 Step 5(빌드 + 테스트)를 **모두 통과**한 경우에만 해당 Phase의 작업들을
`[x]`로 표시한다.

```
- [x] 의존성 설치: ...
- [x] config/env.validation.ts: Zod 스키마로 ...
```

미해결 문제가 남아 있으면 그 작업은 `[ ]`로 두고 이유를 보고한 뒤 **다음 Phase로 넘어가지 않는다**.
(블로킹이 아닌, 단순 기록용 이슈만 남은 경우는 사용자 판단을 받아 진행할 수 있다.)

### Phase 사이클 요약
```
Phase N 구현 완료
  → 명세 검토(CLAUDE.md + PRD) → 수정 / ISSUES 기록 → 재검토
  → npm run build → npm test → 실패 시 수정 → 재실행
  → 모두 통과 → TASKS.md Phase N 전체 [x]
  → Phase N+1 시작
```

## ISSUES.md 기록 규칙 (전 과정 공통)

진행 중 아래 상황이 생기면 레포 루트 `ISSUES.md`에 항목을 **추가(append)**한다. 파일이 없으면
헤더와 함께 새로 만든다.

### 기록 트리거
- **모호함**: 명세(TASKS.md/PRD/CLAUDE.md) 해석이 불명확하거나 서로 충돌할 때
- **보안 우려**: 시크릿이 코드에 노출, 입력 검증 누락, 민감정보가 로그/응답에 노출될 가능성 등
  (CLAUDE.md 6·7장 위반 소지)
- **오류/문제**: 자체적으로 해결하지 못한 빌드·테스트·런타임 문제
- **예측 불가 상황**: 누락된 의존성, 문서와 코드 불일치, 인프라 미비 등 사전에 예상 못 한 상황

### 항목 형식
```
## [Phase 1] 모호함 — serviceDate 경계 처리
- 상황: PRD P7은 KST 자정 기준이나, 마감 직전 제출 시각 처리 명시 없음
- 영향/위험: 하루 1회(P1) 판정이 흔들릴 수 있음
- 분류: 모호함 | 심각도: 중 | 상태: 확인 필요
- 제안: 제출 시각의 serviceDate를 단일 유틸로 산출해 일관 적용
```

분류 값: `모호함` / `보안` / `오류` / `예측 불가`. 심각도: `상`·`중`·`하`. 상태: `확인 필요`·`해결됨`·`보류`.

### 기록 시 주의
- **민감정보 자체를 ISSUES.md에 적지 않는다** — 답변 본문, 쿠키/시크릿 값, 익명 ID 원문 금지
  (CLAUDE.md 7장). 무엇이 문제인지만 추상적으로 기술한다.
- **보안 이슈 또는 블로킹 이슈**는 기록 후 해당 작업을 멈추고 사용자에게 즉시 보고한다.

## 완료 보고

모든 Phase가 끝나면 최종 요약을 출력한다:
```
## 완료 요약
- 구현: Phase 0~3 / 작업 24개 완료 (0개 보류)
- 명세 검토: 수정 3건 처리, 주의 2건 기록
- 빌드: nest build ✓ / 테스트: jest ✓ (또는 "테스트 없음")
- ISSUES.md: 신규 2건 (모호함 1, 예측 불가 1)
- TASKS.md: Phase 0~3 [x] 처리 완료
```

오류·보류로 완료하지 못한 작업은 `[ ]`를 유지하고 사유와 ISSUES.md 참조를 함께 보고한다.
